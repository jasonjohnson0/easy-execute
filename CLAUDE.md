# CLAUDE.md

Guidance for AI assistants working in this repository.

## What this is

**Easy Execute** (branded "LocalDeals" in the UI) — a local-deals marketplace SPA.
Businesses publish deals with trackable QR codes; consumers browse, favorite, print,
and share them. Stripe-backed memberships gate some consumer features, and an admin
dashboard exposes platform-wide analytics and user/business moderation.

Single-page React app, no server of its own. All backend behavior lives in Supabase
(Postgres + RLS + RPC functions + Edge Functions).

The project was scaffolded and is partly maintained through **Lovable**
(https://lovable.dev/projects/edc6a0b7-0ed4-4d87-b7f6-b412445a2fc4). Edits made in the
Lovable editor are committed straight to this repo, so expect commits you did not write
and prefer changes that survive a Lovable round-trip.

## Commands

```bash
npm install          # both package-lock.json and bun.lockb exist; npm is the documented path
npm run dev          # Vite dev server on 0.0.0.0:8080 (host "::")
npm run build        # production build
npm run build:dev    # build with development mode (keeps lovable-tagger plugin)
npm run lint         # eslint over the repo
npm run preview      # serve the built bundle
```

There is **no test suite and no typecheck script**. `npm run lint` and `npm run build`
are the only automated verification available — run both after non-trivial changes.

### Routes (`src/App.tsx`)

`/` Index · `/dashboard` BusinessDashboard · `/business-setup` · `/create-deal` ·
`/favorites` · `/subscription-success` · `/subscription-canceled` ·
`/production` ProductionDashboard · `/admin` AdminDashboard · `*` NotFound.

Every page is `lazy()`-imported. Add new routes **above** the catch-all `*`.

Provider order is `ThemeProvider → BrowserRouter → ErrorBoundary → TooltipProvider`,
with `QueryClientProvider` above `App` in `main.tsx`. Anything calling a router hook
must be rendered inside `BrowserRouter` — past bugs came from violating this.

## Data access patterns

### Supabase client

Import the singleton, never construct a new one:

```ts
import { supabase } from '@/integrations/supabase/client';
```

`src/integrations/supabase/client.ts` and `types.ts` are code-generated by Lovable and
carry a "do not edit" header. The URL and anon key are hardcoded there (and duplicated in
`.env`, which **is committed** — the anon key is public by design, but never add secrets
to it). Regenerate rather than hand-patch these files.

### RPC-first for anything touching business data

Public reads go through `SECURITY DEFINER` Postgres functions, not direct table selects,
so that private business columns (email, phone, address, subscription state) are never
exposed. Follow the existing pattern:

- `get_deals_with_safe_business_info()` — used by `useDeals`
- `get_safe_businesses()` / `get_safe_business_data()` / `get_public_business_info()`
- `get_admin_metrics()`, `get_platform_analytics()`, `get_qr_scan_analytics()`,
  `get_referral_analytics()`, `get_all_users()`, `get_all_businesses()`, `get_all_deals()`
- `has_role(_user_id, _role)` — the admin check
- `is_business_open_now()`, `calculate_distance()`, `get_active_deals_count()`,
  `get_business_count()`

Admin mutations are RPCs too: `admin_ban_user`, `admin_disable_user`, `admin_unban_user`,
`add_admin_role`, `remove_admin_role`, `update_user_profile`.

If you need new public data about a business, add/extend an RPC rather than widening an
RLS policy or selecting `businesses.*` from the client.

### Hooks own the queries

Components do not call Supabase directly (with a few legacy exceptions). Each data
concern gets a `use*` hook in `src/hooks/` that wraps `useQuery`/`useMutation`. Query keys
are string-array literals scoped by id, e.g. `['subscription-status', user?.id]`.

Global query defaults (`main.tsx`): `staleTime` 5 min, `gcTime` 10 min, no retry on 4xx,
up to 3 retries otherwise. Override per-hook when a resource needs fresher data
(`useSubscription` uses a 1-minute stale time and a 5-minute `refetchInterval`).

### Auth

`useAuth()` is a **plain hook, not a context provider**. Every component that calls it
creates its own `onAuthStateChange` subscription and its own profile fetch. Keep this in
mind: calling it in many components multiplies network work, and the hook already guards
against overlapping fetches with an `isProfileFetching` flag.

Critical ordering inside `useAuth` — preserve it if you touch that file:

1. Register `onAuthStateChange` **before** calling `getSession()`.
2. Do only synchronous state updates in the listener; defer any Supabase call with
   `setTimeout(..., 0)` to avoid deadlocking the auth client.

Two user types are distinguished by `user_metadata.user_type`: `'business'` (row in
`businesses`, keyed by auth user id) and `'hunter'` (row in `user_profiles`). Profiles are
created lazily on first authenticated load if missing. Referral codes are stashed in
`localStorage.referralCode` at signup time and consumed when the hunter profile is created.

Admin access: `useAdminAuth()` → `supabase.rpc('has_role', { _user_id, _role: 'admin' })`,
backed by the `user_roles` table and the `app_role` enum (`admin | moderator | user`).
Roles are deliberately in a separate table, never a column on the profile.

## Database

36 migrations under `supabase/migrations/`, named `<timestamp>_<uuid>.sql` by Lovable. Add
new migrations as new files; never rewrite an applied one.

Tables: `businesses`, `deals`, `sponsored_offers`, `business_hours`, `business_audit_log`,
`user_profiles`, `user_roles`, `user_status`, `user_favorites`, `organizations`,
`memberships`, `referral_conversions`, `qr_scans`, `share_clicks`.

Conventions to follow in new SQL:

- RLS enabled on every table, with policies named as readable sentences
  ("Business owners can update their own deals", "Anyone can view active deals").
- Cross-table permission checks go through `SECURITY DEFINER` functions with an explicit
  `SET search_path` — never write a policy that self-references its own table's RLS.
- `updated_at` is maintained by the shared `update_updated_at_column()` trigger.

## Edge Functions (`supabase/functions/`)

`check-subscription`, `create-subscription-checkout`, `customer-portal` — Deno, deployed by
Lovable/Supabase, all with `verify_jwt = true` in `config.toml`. House style in each:

- `corsHeaders` const, early return on `OPTIONS`.
- A `logStep(step, details)` helper prefixed with the function name.
- Service-role Supabase client + `auth.getUser(token)` from the `Authorization` header.
- Always return JSON, `status: 500` with `{ error }` on failure.

Secrets (`STRIPE_SECRET_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) live in the Supabase dashboard,
not in this repo. Client code invokes these with `supabase.functions.invoke(name, { body })`.

Membership flow: `useSubscription` checks `memberships` first, falls back to the Stripe API,
and backfills a `memberships` row when Stripe says the subscription is active. Checkout and
portal URLs are opened with `window.open(url, '_blank')`.

## Styling

Tailwind with a semantic token system defined in `src/index.css` and mapped in
`tailwind.config.ts`. **Use semantic classes (`bg-primary`, `text-muted-foreground`,
`border-border`), not raw palette colors (`bg-teal-700`)** — dark mode is driven entirely
by the `.dark` token overrides, so hardcoded colors break it.

Available beyond stock shadcn: `primary-light`, `primary-glow`, `secondary-light/dark`,
`success`, `warning`, gradient vars (`--gradient-hero`, `--gradient-deal`…), shadow vars
(`--shadow-deal`, `--shadow-glow`), and transition vars. Radius base is `0.75rem`.

Theme switching is `next-themes` with `attribute="class"`, `defaultTheme="system"`.

Add shadcn primitives with the CLI (`components.json` is configured: aliases `@/components`,
`@/lib/utils`, `@/components/ui`, `@/hooks`; base color slate; CSS variables on). The repo
also has hand-written wrappers alongside them — `validated-input`, `validated-select`,
`validated-textarea`, `validated-date-picker`, `phone-input`, `email-input`, `deal-skeleton`
— re-exported from `src/components/ui/validation/index.ts`. Prefer those for forms.

## Validation & security

- Zod schemas live in `src/lib/validations/schemas.ts` and **fold sanitization into the
  schema** via `.transform(sanitizeInput | sanitizeHTML | sanitizeEmail | sanitizePhone)`.
  New user-facing input should get a schema there rather than ad-hoc checks.
- `useValidatedForm` (and `useDealForm`, `useBusinessForm`, `useAuthForm`) wrap
  react-hook-form + `zodResolver`.
- `src/lib/security/sanitization.ts` — DOMPurify wrappers with a tight allow-list, plus a
  `RateLimiter` class. Two instances: `authRateLimiter` (5 per 5 min, applied in `signIn`)
  and `apiRateLimiter` (50/min).
- `src/lib/security/headers.ts` — the CSP string **hardcodes the Supabase project URL** in
  `script-src`/`connect-src`. If the project ever changes, this must change with it.
  `applySecurityHeaders()` also force-redirects to HTTPS off localhost.
- `src/lib/security/businessData.ts` — the sanctioned read/update path for business rows,
  plus `logBusinessAccess()` writing to `business_audit_log` (failures are swallowed by
  design so auditing never breaks a user flow).

Note `src/lib/validations/utils.ts` exports its own regex-based `sanitizeHTML` that is
*not* the DOMPurify one. For anything rendered as HTML, use the version in
`lib/security/sanitization.ts`.

## Analytics

Two independent layers:

1. **Supabase tables** — `useAnalyticsTracking()` inserts into `qr_scans` and
   `share_clicks`. These feed the admin/business dashboards through the analytics RPCs.
2. **`src/lib/analytics/tracker.ts`** — a client-side singleton that logs to the console
   (`🔍 Analytics Event:`) and persists the last 100 events in `localStorage`
   (`analytics_events`). There is no analytics backend endpoint yet.

URL contract (documented in `ANALYTICS_IMPLEMENTATION.md`, consumed in `src/pages/Index.tsx`):

- Share link: `/?deal=<id>&ref=<orgKeyword>`
- QR code: `/?deal=<id>&qr=true&ref=<orgKeyword>` — the `qr=true` flag is what prevents
  double-counting scans against shares.
- Bare referral: `/?ref=<orgKeyword>`

`Index.tsx` reads these params, fires the right tracking call, then clears them from the URL.

## Gotchas

- **Service worker is deliberately disabled.** `public/sw.js` is a kill-switch that purges
  its caches and unregisters itself, and `main.tsx` unregisters any surviving registration
  on boot. `src/lib/pwa/serviceWorker.ts` still contains a `register()` helper but **nothing
  calls it** — do not re-enable it without understanding the stale-bundle incident recorded
  in `.lovable/plan.md`. PWA install prompt (`lib/pwa/installHook.ts`) is unaffected.
- **TypeScript is loose**: `strict: false`, `noImplicitAny: false`, `noUnusedLocals: false`.
  `any` appears throughout. Don't assume the compiler will catch a type mistake — and don't
  do a repo-wide strictness migration as a side effect of an unrelated task.
- **`USE_MOCK_DEALS`** in `src/data/mockData.ts` short-circuits `useDeals` to fixtures. It
  ships as `false`; make sure it stays that way.
- **Dead code**: `src/pages/CreateDealEnhanced.tsx` and `src/components/ValidationShowcase.tsx`
  are not imported or routed anywhere. `/create-deal` uses `CreateDeal.tsx`. Edit the routed
  one.
- **Debug logging** — `useAdminAuth` and `AdminDashboard` are noisy with `console.log`. That
  is existing behavior, not a bug to fix opportunistically, but don't add more.
- ESLint treats unused vars as an **error** (`argsIgnorePattern: "^_"`,
  `ignoreRestSiblings`). `react-refresh/only-export-components` is a warning, which is why
  some `ui/` files export both components and helpers.
- Two lockfiles exist (`package-lock.json`, `bun.lockb`). Whichever you use, don't commit a
  churned version of the other.

## Working conventions

- Import with the `@/` alias; relative imports are rare and mostly inside `components/ui/`.
- Feature components are `PascalCase.tsx` with **named** exports; pages use **default**
  exports (required by `lazy()`).
- New data fetching → a hook, not inline `supabase` calls in a component.
- New public data about businesses → an RPC, not a relaxed RLS policy.
- New form → a zod schema in `lib/validations/schemas.ts` + the validated input wrappers.
- After changes, run `npm run lint` and `npm run build`; there is nothing else to verify with.
